# 07 · 批量上传配额修复与内置实景图库

- **日期**：2026-10-31
- **对应模块**：`src/js/modules/storage.js`、`src/js/modules/ui.js`、`src/js/modules/map.js`、`src/js/data/gallery.js`
- **目标**：让「一次导入 48 张真实非遗照片」这件事既不失败、也看得见结果

---

## 背景：一个被误诊的 Bug

用户反馈：用应用的「📁 批量上传」导入非遗实景照片时，弹出提示

> 各图片存储超过 1M，存储失败

这条提示来自 AI 初版代码，**把问题归因到了"单张图片太大"**。选手复盘后判断这个归因是错的：

1. 上传前已经过 Canvas 等比压缩，实测单张仅 60–160KB，**不存在"超过 1MB"的图片**；
2. 真正爆掉的是 **LocalStorage 的整源 5MB 总配额** —— 48 张 × 约 100KB × Base64 膨胀 33% ≈ 6.4MB，必然溢出；
3. 提示文案误导了排查方向，属于典型的"错误归因"缺陷。

**结论：这不是参数问题，是持久层的选型问题。**

---

## Prompt 原文（第二轮）

```
批量上传 48 张非遗照片时，提示「各图片存储超过 1M，存储失败」。
但压缩后每张只有 60~160KB，明显不是单张太大的问题。

请重新分析根因，并给出修复方案。要求：
1. 不要再改压缩参数，压缩不是瓶颈；
2. 允许更换持久层，但必须保证老用户已上传的数据不丢；
3. 批量上传要有可见的进度反馈，不能只弹一个失败提示；
4. 如果新的持久层不可用，必须有降级回退，不能白屏。
```

## AI 产出摘要

AI 认同了「整源配额」的根因判断，给出把持久层从 LocalStorage 迁移到
**IndexedDB** 的方案，并给出「打开数据库 → 全量载入内存 → 首次启动迁移旧数据 →
写失败则降级回 LocalStorage」的骨架。

## 选手评审与干预

| 问题 | 修复 |
| --- | --- |
| 所有 API 变成异步，但 `getImage()` 被同步调用了十几处 | 保留内存镜像 `userImages` 作为同步读，IndexedDB 只做**写穿 + 启动时预热**，避免全站异步化 |
| 上传是异步写入，`pagehide` 时可能还没落盘 | 增加 `pending` 计数 + `flush()` 返回 Promise，批量上传结束前 `await flush()` |
| 旧版 LocalStorage 数据迁移后没清理，占用配额 | 迁移成功后 `removeItem('fj_imgs_v4')`，并保留 try/catch 容错 |
| 批量上传全程同步循环，进度浮层根本渲染不出来 | 每处理完一张 `await new Promise(r => setTimeout(r, 0))` 让出主线程 |
| 上传后只刷新了地图标记，问答卡片和详情弹窗还是旧图 | 抽出 `applyImage()`，同时刷新标记 + 卡片 + 详情，并加「我的照片」角标 |
| 仍依赖在线图库，弱网 / 断网时体验差 | 48 张实景照片离线压缩后**随包内置**，建立「用户上传 > 内置图库 > 在线图库」三级优先级 |

## 效果对比

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 批量上传 48 张 | ❌ 报「存储失败」 | ✅ **48 / 48 成功** |
| 存储后端 | LocalStorage（5MB 整源上限） | **IndexedDB**（配额按磁盘容量） |
| 实测耗时 | —— | **约 1 秒** |
| 刷新后 | —— | **48 条完整保留** |
| 首屏图片来源 | 在线拉取，受网络波动影响 | **内置本地文件，零网络依赖** |
| 控制台 404 | 1 条（`env.generated.js`） | **0 条** |

## 最终落地

- `storage.js` 承载 IndexedDB 持久化、启动预热、旧数据迁移、`flush()` 落盘等待与降级回退；
- `data/gallery.js` + `assets/sites/*.jpg` 构成内置实景图库（48 张 / 约 3.1MB）；
- `ui.js` 的批量上传补齐进度条、成功/失败计数、未匹配清单与「我的照片」角标；
- 该修复由端到端脚本验证：投喂 48 个真实文件 → 全部匹配保存 → 刷新后复查 IndexedDB 仍为 48 条。

> **复盘一句话**：AI 会把「异常现象」当成「问题原因」。当提示说"图片超过 1MB"时，
> 最容易犯的错就是去调小图片 —— 而正确答案是换掉装图片的容器。
