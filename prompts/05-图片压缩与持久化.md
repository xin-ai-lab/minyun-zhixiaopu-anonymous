# 05 · 图片上传、压缩与持久化

- **日期**：2026-10-29
- **对应模块**：`src/js/modules/image.js`、`src/js/modules/storage.js`
- **目标**：让用户能上传真实非遗照片，且刷新页面后不丢失

---

## Prompt 原文（第一轮）

```
这是个纯前端项目，没有后端和数据库。
我想让用户能上传非遗项目的照片，并且刷新页面后照片还在。
请给出实现方案。
```

## AI 产出摘要

建议使用 `FileReader.readAsDataURL()` 把图片转为 Base64，写入 `localStorage`，
并在页面加载时读回渲染。

## 选手评审与干预（发现致命缺陷）

**实测现象**：上传一张 3.5MB 的手机原图后：

1. 浏览器抛出 `QuotaExceededError`（LocalStorage 单域名配额通常仅 5MB）；
2. 且由于 Base64 编码膨胀约 33%，单张图就占满配额；
3. 未捕获异常导致后续逻辑中断，页面卡死。

**根因**：AI 初版完全忽略了「LocalStorage 容量有限」这一硬约束。

---

## Prompt 原文（第二轮，引入压缩）

```
AI 初版方案在真实场景会崩溃，因为 LocalStorage 只有 5MB。
请帮我改写：在上传阶段就用 Canvas 做前端压缩。

【压缩要求】
- 等比缩放：最长边限制在 800px 以内（小于则保持原尺寸，不放大）
- 输出格式：JPEG
- 输出质量：0.85
- 用 Promise 封装，便于 await

【健壮性要求】
- 文件读取失败、图片解码失败都要 reject，不能吞掉异常
- 写入 LocalStorage 失败时给出友好提示，不能静默失败
```

## AI 产出摘要

输出了基于 `Canvas.drawImage()` + `toDataURL('image/jpeg', 0.85)` 的压缩函数。

## 选手评审与干预

| 问题 | 修复 |
| --- | --- |
| 小图被"放大"到 800px，反而更糊 | 增加判断：仅当边长**超过**上限时才缩放 |
| 横图 / 竖图缩放逻辑混淆 | 分情况处理：`w > h && w > MAX` 与 `h > MAX` 两条分支 |
| LocalStorage 数据损坏时应用启动崩溃 | `readJSON()` 包 try/catch，读失败回退空对象 |
| 在线图库图片全部都塞进 LocalStorage | 改为**分离缓存**：在线图只存 URL（轻量），仅用户上传图存 Base64 |
| 图片检索接口被高频请求触发限流 | 逐张拉取，间隔 150ms（`WIKI.FETCH_INTERVAL`） |

## 效果对比

| 指标 | 优化前 | 优化后 |
| --- | --- | --- |
| 单图体积 | ~3.5MB（原图 Base64） | **~60-120KB** |
| 可存储数量 | 1 张即溢出 | **40+ 张** |
| 页面稳定性 | 上传大图即卡死 | 稳定 |
| 刷新后 | 丢失 | **保留** |

## 最终落地

`image.js` 负责压缩，`storage.js` 负责持久化与开放图库检索，
二者解耦且均带完整异常处理；所有压缩参数收纳于 `config.js` 的 `IMAGE` 节点。
